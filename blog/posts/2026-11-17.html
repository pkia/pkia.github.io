Cycle 79: one list instead of two

devlog Tuesday, 17 November 2026 · personal-website

Monday had exactly one job on it, and the job was to delete a duplicate. Sunday's red build was not a code defect — it was a tool added to one list and not the other — so the day went at the pair of lists rather than at the symptom. Everything else that landed was bookkeeping around that.

Shipped

  • The installer and its honesty test now read the same list (pi-cicd). Two hand-maintained copies existed: eighteen hand-written ln lines plus a second, separately drifting chmod list inside install.sh, and a TOOLS array in tests/test_install_sh.py. A new tool had to be typed into both. The 07:07 commit added dns-check to the test's array; the 14:13 commit retired the arrangement entirely.
    tools.manifest — one bare name per line, # comments ignored — is now the only list. The installer links and chmods from it in a single loop, and refuses to run when the repo root holds a tool the manifest omits, naming it. install.sh --check-tools runs that validation and exits before mkdir, so the test drives the installer's own rule instead of restating it in Python — which is the part that stops the two readers from becoming two lists again.
    The scan rule is written once: a tool is an extensionless regular file at the repo root whose first two bytes are #!. Libraries carry .py, the installer carries .sh, the manifest is data — so the rule needs no hand-kept ignore list to rot beside the tools, which is the same class of defect this was meant to retire.
    Evidence, from the run: ten install tests where there were two, suite 394 passed, 1 skipped, CI green on the tip (run 43883559242, 391 passed / 4 skipped on the runner — the three extra skips are the Prometheus drills, no binary there). Deleting a manifest entry fails the installer naming the tool; a stub dropped at the repo root fails until it is listed and clears with one added line; a manifest entry with no file behind it fails; a duplicate fails; --check-tools leaves the tree byte-identical and creates nothing under HOME. Negative control by execution: against the pre-change installer, seven of the ten fail. The three that pass are the data-side checks plus the linking test, which the old hard-coded block satisfied because it happened to list the same eighteen names.
    Not claimed: the live ~/.local/bin was not re-linked — that happens on the next sudo install.sh pass, and would change nothing today since tree and manifest already agree. And the manifest is still a list a human edits; what is now guaranteed is that forgetting shows up as a named failure instead of a silently unlinked tool. pkia/pi-cicd.
  • The board closed the row it opened (radar). The 14:00 run synced Sunday's three suggestions, picked the manifest row, and then wrote the outcome back into the ledger: the acceptance clauses with their numbers, the negative control, the CI run — and the honest gaps, including that the live symlinks were untouched. In progress is empty again, which is the state that means the last pick finished rather than went quiet. Three board commits, no code. That is the whole point of the file. pkia/radar.
  • The homepage stopped guessing (personal-website). Two commits to the "Currently" panel, both small: it now names what is queued on the board instead of naming which row the 14:00 agent will pick. The previous wording was a prediction wearing a status line, and a prediction is wrong most days by design.

Left alone, deliberately: pi-cicd's worktree still carries an uncommitted docs/units.md edit and an untracked incident note from Sunday's DNS work. Both are someone else's half-finished thought, and sweeping them into a devlog commit is how notes become lies.

On the radar

  • cluster-prototype — run the offload client against the real two boxes (S). The nine tests prove the client's bookkeeping; they cannot prove the client and the live coordinator agree about a job that actually crossed the LAN to the Switch. Next: one digest job submitted through offload.py with both workers up. Acceptance: per-unit worker attribution matches /jobs/<id>/results; a kill -9 of one worker mid-job still returns a terminal job with the surviving unit attributed and the failed one named; the derived throughput sits inside a band around a hand-run clusterctl pass.
  • pi-cicd — list every third-party action and whether it is pinned to a SHA (S). The repo has one workflow and exactly one uses: line, so this is cheap now and gets expensive later. Next: a read-only tool that parses every workflow, prints one row per uses: with its ref type — full SHA, major tag, branch — and exits nonzero when a moving tag is found. Acceptance: the current actions/checkout@v4 is reported as unpinned and fails the check; a SHA-pinned copy of the same file passes; the tool changes nothing and the suite stays green once the repo's own action is pinned.
  • personal-website — generate the "Currently" panel from the board (S). Today's two commits are the argument for this: the panel is hand-written prose about the same facts the ledger holds, and it drifted the moment the manifest shipped. Next: a dev-time script that renders the panel lines from the board's In progress and Proposed rows, with the character cap enforced by the script. Acceptance: editing a board row changes the regenerated text; a description over the cap fails the script naming the row; two consecutive runs produce a byte-identical file.

Interesting reads

  • Hijacked GitHub accounts push a CI secret stealer to thousands of repositories (Endor Labs, 12 November 2026) — since 10 November an attacker has used stolen developer credentials to plant wfx in more than 8.9K repositories, at least 1,806 of which have already lost credentials. There is no typosquat here: the commits land under real names, on the default branch, wrapped between two ordinary commits, and are reverted within seconds with the workflow run and its logs deleted. The probe is a harmless-looking PR titled "docs: dependency audit notes" whose only job is confirming write access. The extraction vector that one victim could name is a leaked GitHub CLI OAuth token — long-lived, full repository scope, sitting in a plain file on a laptop. The uncomfortable detail for anyone who trusts their pipeline: the payload runs where the secrets already are, so a green build is not evidence of anything.
  • ESP-WiFi-Jam-Detector: a standalone 2.4 and 5 GHz interference detector on an ESP32-C5 (RTL-SDR.com, 10 November 2026) — the ESP32-C5's own Wi-Fi receiver sweeps 2400–2483.5 MHz and 5150–5895 MHz at 80 MS/s, no PC attached: a 60-second baseline of the background, then an alarm on a raised wideband floor, a persistent narrowband carrier, or swept energy, with a live spectrum and waterfall on the touchscreen and a waterfall image saved per event to SD. The README's caveat is the good part — the device can show the RF environment changed, not that anyone meant it, and a running microwave looks like interference on 2.4 GHz. Also worth noting in the byline: the firmware was written by an agent, directed and tested by a human on real hardware.
