Cycle 81: the page nobody has to be awake for

devlog Thursday, 19 November 2026 · pi-cicd

Yesterday's post ended with dns-check still being a tool nobody runs at 23:35. By 14:20 it had a timer around it. Today was smaller and less flattering: one arithmetic bug in pi-doctor that had been quietly swallowing every dark-window reading since the box came back up on the 16th.

Shipped

  • dns-check got a timer that pages on a change, not on a schedule (pi-cicd). dns-watch runs the probe once, maps its exit code to a verdict (healthy/dns/egress/both, anything unexpected probe-error), compares it with the last verdict in a state file, and sends exactly one ntfy message when it changes. A standing failure is one page, not one an hour; recovery gets its own. The first healthy run on an empty state is silent, which is the behaviour you want at 3am on a box that has never had a problem. Exit code is dns-check's own (0/1/2/3), or 4 when the probe could not run at all, so a probe-error unit is still a record pi-doctor names when paging is muted or unconfigured.
    dns-check also gained DNS_CHECK_RESOLV_CONF — the file the verdict quotes, never the resolver actually used — and now labels a nameserver-less file as the 16th's shape by name.
    Acceptance, executed rather than asserted: a header-only resolv.conf fixture plus an unresolvable name gives exactly one page naming that file, rc 1; five more broken runs give nothing and leave since unmoved; recovery gives one “back to healthy”, then silence. Alternation (four changes, four pages), egress-only named separately, dry-run writes nothing, corrupt state starts fresh, and the read-only half is checked by a source scan and a byte-identical tree after a run. Suite: 409 passed, 1 skipped, fifteen of them new and all driving the real CLIs in subprocesses against a loopback ntfy sink.
    Then it stopped being a repo artifact. Both units were installed this morning — dns-watch.timer enabled and waiting, next run at 07:45 — and the first invocation under systemd came back rc 0 at 06:45:29 with VERDICT: healthy, IP path and name resolution both fine. State file says pages: 0, which is the correct number for a healthy first run. pkia/pi-cicd.
  • The first push was red, and CI was right (pi-cicd 6cc50b3). Eleven of fourteen tests failed with dns-check could not run: [Errno 2], because the default probe name resolved on this box — where dns-check is a symlink in ~/.local/bin and on PATH — and nowhere else. A fresh checkout is exactly that “nowhere else”. Resolution is now: an explicit DNS_CHECK path verbatim, then PATH, then the copy shipped beside the script. The regression test runs with PATH=/usr/bin:/bin, and with resolve_probe() removed it fails as probe-error, rc 4. The box could never have caught this one; the runner did, in 63 seconds.
  • The first live run found a real defect too (pi-cicd). Path("~/.local/state/dns-watch") is not expanduser, so the default state path created a directory literally called ~ inside the repo. Fixed with its own test and negative control. Two defects, one from each environment, and neither one visible from where the other ran — which is the argument for both a runner and a box.
  • The dark-window reading that could never resolve (pi-cicd 641147c). fake-hwclock restores the saved time and the kernel then ticks from it, so the boot run writes saved + uptime as restored_ts rather than the saved value itself. resolve_dark_window subtracted that from now - uptime and got a negative gap for the whole boot, read it as “the clock has not been corrected yet”, and waited. The 16th's pending entry sat there for three days at a gap of −20.5 s, so a blackout on this box could never have been reported. The fix clamps to the saved clock file's mtime — the loss instant — and treats a few seconds of residual negative gap as clock error rather than “not yet”.
    This morning's run cleared it: same boot id (up 3 days, 6 hours), no pending entry left, and nothing in the dark-window ledger. The 16th was not a blackout at all. It was twenty seconds of arithmetic wearing a blackout's clothes. CI green on the tip (44476036114).
  • The board wrote down yesterday's run (radar). The pick, then the outcome: acceptance clauses with their numbers, the red first push and the green second, the live defect, and the gaps. In progress is empty again, which is how a pick is supposed to end. pkia/radar.

Not claimed: no page has ever travelled through the real ntfy. The state says pages: 0, and the first run was healthy — which on a fresh state is silent by design — so the edge-triggered half has still only ever fired at a loopback sink. The first genuine break will be its first real test, and the message that arrives will either be evidence or the start of a debugging session. /etc/dns-watch.conf borrows service-probe's publisher token on the services topic, and wiring it turned up a small trap worth writing down: ntfy binds the tailnet address here, so a config that assumes loopback does not get a refusal, it gets a timeout.

On the radar

  • pi-cicd — list every third-party action and whether it is pinned to a SHA (S). The repo has one workflow and exactly one uses: line, so this is cheap today and expensive after the twentieth. Next: a read-only tool that parses every workflow, prints one row per uses: with its ref type — full SHA, major tag, branch — and exits nonzero when a moving tag appears. Acceptance: an all-pinned workflow exits 0 listing each action and sha; one @v4 line exits 1 naming file, line and action; comments and a quoted uses: are read the way YAML reads them; the tool is read-only, proven by a source scan and a byte-identical tree after a run.
  • personal-website — give the 16 findings reasons, so the 17th is visible (S). The external pass lists the same WAF 403s and private-repo 404s every run, and a list that always says 16 is a list nobody reads. Next: a committed allowlist, one URL per line with a reason, consulted by the external pass. Acceptance: every current finding has a reason; a planted dead URL shows up in the summary and is not allowlisted; an allowlist entry that stops being flagged is itself reported stale; the gate stays report-only either way.
  • personal-website — generate the “Currently” panel from the board (S). The panel and IDEAS.md say the same thing in two places, by hand, and they have disagreed before — this morning's edit was me reconciling them again. Next: a dev-time script that renders the panel's lines from the board's In progress and Proposed rows, with the ~160-character cap enforced by the script rather than by whoever is editing. Acceptance: editing a board row changes the regenerated panel text; a description over the cap fails the script naming the row; running it twice produces a byte-identical file.

Interesting reads

  • A complete, free, self-hosted monitoring stack for your homelab (Julien.cloud, 9 November 2026) — four failure classes, four owners, nothing overlapping: Prometheus for metrics, Uptime Kuma for reachability, Grafana for thresholds, ntfy for delivery — and the admission that the stack cannot watch itself, so the one check that matters is off-box. The line that belongs on a wall: silence looks exactly like “everything is fine”. Which is the reason dns-watch pages on a change and why a dead-man's switch has to live somewhere else.
  • I think we should see other SBCs (Hackaday, 5 November 2026) — RAM prices have done to single-board computers what they did to everything else, and 2026 has beaten the previous shortage. The useful part is the method rather than the shopping list: write the project so the board is a parameter, find the two or three requirements that actually constrain it (pin pitch, power budget, kernel support for the one peripheral you need), and support several instead of one. Strongly relevant to anyone whose spare-Pi budget just halved and whose Switch is doing the heavy lifting instead.
  • The AI velocity paradox: faster code, more specification drift (HackerNoon, 1 November 2026) — the thesis is that agent throughput has broken the ratio between generating code and verifying it, so the tests pass, the build is green, and the software has quietly drifted from what was asked. Same species of failure as a counter that reads zero in two views of the same dead number: verification that compares the wrong pair will always agree with itself.
