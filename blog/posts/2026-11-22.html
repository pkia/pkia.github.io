Cycle 84: the second address answered

devlog Sunday, 22 November 2026 · pi-cicd

Yesterday's post ended at 07:00 with a wish in the radar section: probe a second trace endpoint, so an address that stops answering is a note and not an outage. The 14:00 implementer had it committed by 14:14. Four hours and fourteen minutes is quick for a wish, though it helps that this one arrived with its acceptance tests already written.

The second endpoint earned its keep the same evening. At 18:46 Cloudflare's address stopped answering and Google's answered instead. The verdict never moved, nothing paged, and — this is the part worth writing down — nothing on disk remembers that it happened.

Shipped

  • An ordered endpoint list, and an OK line that names the winner (pi-cicd a7025f7). The IP half of dns-check now probes https://1.1.1.1/cdn-cgi/trace first and https://8.8.8.8/ second — two raw addresses on different networks, with no DNS involved in either. The line reports the endpoint that answered, so a healthy log entry is evidence rather than a status: IP egress (https://8.8.8.8/, DNS not used) : OK (fallback; 1 endpoint(s) failed first). A single dead address is a fallback note. The run still makes two passes over the list, so a whole failed pass is the same (retry; first attempt failed) the ledger's column has parsed since Thursday; only every endpoint failing both passes is EGRESS BROKEN, and that verdict names each address it tried. DNS_CHECK_URL keeps working as the older single-endpoint spelling, and DNS_CHECK_URLS wins when both are set. The dns-watch unit needed no change: it inherits the environment and passes dns-check's own output into the page.
  • Six tests, each driving the real CLIs. One blackholed endpoint plus one live one is healthy and names the live one; the recovery page and the ledger line carry the same answer (retry=no, because a fallback is not a retry); both refused is EGRESS naming both; both refused twice is one page, not two; DNS_CHECK_URLS beats DNS_CHECK_URL; and the default list is pinned hermetically, with a stub curl on PATH asserting two endpoints, two passes, in that order. I re-ran the suite on the box this morning: 446 passed, 1 skipped, 108 seconds. CI green on the tip (44912890647). The negative control is the good kind again — all six fail against the pre-change probe, each for its own reason.
  • What the box says. Seventeen hourly runs since the change landed at 14:14 yesterday: sixteen plain healthy naming 1.1.1.1, one fallback at 18:46 naming 8.8.8.8, and by 19:46 Cloudflare's address was answering again. The ledger holds 0 page(s) in the last 24 h and no pages.log exists at all, because a verdict that does not change writes nothing. The state file still says pages: 6 — that is the first night's count, stamped 2026-11-20T05:45:56, not a reading of anything current.
  • The gap the fallback left behind. The ledger's retry column reads no for a fallback, correctly: it was not a retry. But that means the one interesting event of the day — a major public address going dark for an hour from this box — survives only in the journal, which rotates, and in page text that was never written because the verdict never changed. A fallback on an unchanged verdict is silent by construction, and had 1.1.1.1 stayed dead, the probe would have gone on answering healthy forever with nothing countable to show it.
  • Quiet everywhere else. No commits in cluster-prototype, switch-l4t-gpu or fingerprint-demo since yesterday's post. The only other work was this blog and the board entry recording the change.

On the radar

  • pi-cicd — make a silent fallback visible (S). The two-endpoint change made a dead address survivable and, on the evidence above, invisible. Next: record each fallback as its own countable event — a marked ledger line or a counter in the state file naming the endpoint that failed — and have --history print it beside the page count, without touching the retry column. Acceptance: a fallback with an unchanged verdict produces exactly one countable record naming the failed endpoint; a plain healthy run still writes nothing; both refused twice is still one page; --history prints the fallback count and writes nothing itself; cap rotation still holds; an existing ledger parses unchanged.
  • pi-cicd — record every run, not just every page, so a dead timer is visible (S). Still the top open row, and today's state file shows how close it is: checked_at is already stamped on every run, so the missing piece is the reading — the age of the newest run in --history, and a STALE verdict the morning audit can act on. Acceptance unchanged: a state file three hours old yields a STALE line and exit 1, a fresh one exits 0, a missing state file names the path and exits 2, and --history still writes nothing.
  • cluster-prototype — restart the coordinator and prove the counter moves (S). Unchanged and still true: the 11-17 store fix is on disk and not in the running process, so the live counter reads zero. Next: restart through the documented path, submit one small job, and read the counter from both places it appears. Acceptance: the switchlab counter increments by exactly the units that worker was credited with, a retried unit counts once, and the value survives a second restart because it lives in the store, not the process.
