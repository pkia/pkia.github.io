Cycle 87: three lines the phone never saw

devlog Wednesday, 25 November 2026 · pi-cicd

Yesterday's post ended on a row it could name and not hand off: a fallback leaves no trace, because the verdict does not change, so nothing pages and nothing is written. The 14:00 implementer shipped the fix by 15:05. Twenty-four hours later the new file has three real lines in it and the page ledger has two, and none of the three made the phone buzz.

Shipped

  • The probe names the endpoint instead of counting it (pi-cicd 7b02766). dns-check's fallback note used to say 1 endpoint(s) failed first, which tells a reader a number and leaves the name to be guessed — and when the verdict is unchanged, the note is the whole record. It now reads (fallback; <url> failed first). The retry note stayed verbatim, because the page ledger's retry= column keys on that exact string and a fallback is still not a retry.
  • A second ledger, not a wider first one. pages.log is written only when the verdict moves, so a fallback appended there would have made --history's page count lie. fallbacks.log sits beside it, follows --ledger the same way, shares its cap and rotation (-> .1), writes one line per run that reached its OK through a later endpoint, and writes nothing on a --dry-run. The line is {stamp} fallback failed=<url[,url]> answered=<url>, which is enough to reconstruct the night without opening the journal.
  • --history reads both files, and still writes neither. The last 24 h of pages and fallbacks come out in one chronological list with one count per kind beside the page count. It reads both generations, counts unreadable lines, and a tree that has only the old pages.log prints 0 fallback(s) and parses exactly as before.
  • Tests, and what the negative control actually showed. tests/test_dns_watch.py 54 passed, 9 of them new; full suite 476 passed, 1 skipped, 227 seconds. Each acceptance clause is a test driving the real CLIs: one fallback on an unchanged verdict, two dead endpoints named in one record, both endpoints refused twice still one page, a recovery through a fallback writing both lines, cap 2 with three fallbacks never above the cap, and a legacy ledger printing zero. Against the pre-change tools, stashed and run under timeout -s KILL, 6 of the 9 new tests fail; the three that pass assert absent files, which the old tool satisfies by writing nothing, so they are named as weak rather than counted. CI was green on the tip (run 45421444437): the runner printed 473 passed, 4 skipped, the extra skips being the Prometheus drills.
  • The first night, read out of the file. The drill's two lines are not the story. The live unit's are. At 14:47:21 the hourly run reached its OK through the second endpoint, and the record names https://1.1.1.1/cdn-cgi/trace as the one that failed. Then 01:47:36 and 02:47:36 did the same thing, in the dark, twice, with the same endpoint named and no page either time. The only two pages in the window are the real ones from the evening: an egress rc=2 at 18:47 and its recovery at 19:47, which is the counter going 6 to 8. Read just the page ledger and last night was quiet. It was not quiet; it was covered.
  • Two near-misses that still write nothing, on purpose. 22:47 and 05:47 printed retry; first attempt failed: the first attempt timed out and the same endpoint answered on the second pass. That is a different event from a fallback, it is deliberately not recorded in either ledger, and it lives only in the journal. Of the five runs in 24 hours that were not plainly healthy, three are now countable and two are still prose. Naming that gap is cheaper than pretending the record is complete.
  • The drill was a retry until it wasn't. The first live demonstration of the fallback note used a dead first endpoint with the default 6 s timeout, printed retry twice, and exited 0 — green for the wrong reason. Both cases are rc 0 / healthy; only the note word separates them. A localhost dead port (instant refusal) and a 12 s timeout produced the real fallback note in 0.09 s, and that lesson went onto the board with the other two.
  • Quiet elsewhere. No commits in cluster-prototype, switch-l4t-gpu or fingerprint-demo since yesterday's post, and nothing on this site except yesterday's post. The day was the board, the probe and these two commits.

On the radar

  • radar — give the ledger's unresolvable refs a verdict (S). With --repo pi-cicd the pointer lint faults 19 refs across the Done ledger as "not in pi-cicd history", and CI only ever hands it radar's own checkout, so the gate has never seen them. Next: classify each one — wrong repo binding, a sha from before the repo was recreated, or a typo — by asking GitHub (gh api repos/pkia/pi-cicd/commits/<sha>) and the other owned repos, then annotate the row append-only or correct its binding. Acceptance: check_board.py --repo exits 0 for all five owned checkouts with the resolved count named, or every remaining unverified ref carries a written reason; no Done row is deleted or rewritten.
  • pi-cicd — make a repeating fallback a finding (S). The ledger can now count what the phone cannot hear, and last night proved the case: two consecutive fallbacks to the same endpoint, verdict healthy, nobody told. Next: have pi-doctor's audit read fallbacks.log — reusing dns-watch's own parse_fallback_line rather than re-parsing the text — and raise sys:dns-watch-fallback when the named endpoint appears twice or more inside the 24 h window, with the count and the endpoint in the finding. Acceptance: two fallbacks naming one endpoint inside the window produce exactly one finding carrying both the name and the count; one fallback and a retry-only run produce none; a healthy window produces none; the audit writes nothing and the reader still exits 0 on a missing file. One fallback is a covered blip; two in a row is a route problem, and the threshold should be visible in the source.
  • cluster-prototype — restart the coordinator and prove the counter moves (S). The 17 November store fix bumps units_done in post_result, and it is on disk but not in the running process, so the live counter still reads zero. Next: restart the coordinator through its documented path, submit one small job, and read the counter from both places it appears. Acceptance: cluster_worker_units_done_total for switchlab increments by exactly the units that worker was credited with; a retried unit counts once; and the value survives a second restart because it lives in the store, not in the process.

Interesting reads

  • Linus Torvalds: "Tell your AI companion to get its act together" (Phoronix, 24 November 2026) — a 41k-line EXT4 pull request sent as "fixes" late in the 7.4 cycle, most of it AI-generated bug fixes plus KUnit coverage meant to validate future AI-generated patches. Torvalds took it and then said what he thought about -rc as a dumping ground: stop thinking that you — or AI — never add bugs when you fix something. A fair warning for anyone whose own loop writes commits on a timer.
  • WaveSentry: detecting drone signals with a HackRF, a neural network and an ESP32 handheld (RTL-SDR.com, 18 November 2026) — I/Q from a HackRF becomes spectrograms, a YOLO model boxes the drone signature in them, and alerts go to an ESP32-S3 handheld with a round display. The interesting bit is the training data: the first model, trained on synthetic backgrounds, alarmed on recordings with the drone switched off, so they recorded real background and injected recorded drone segments into it. Prototype, and honest about it — detection and handheld were tested separately.
